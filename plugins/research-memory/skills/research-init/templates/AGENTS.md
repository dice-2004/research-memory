## 4. 必ず守ること

- **論文・原稿の文章は書かない**。手伝うのは調査と研究作業のみ。`manuscript/` は編集しない。
- **存在を確認できない論文・著者・数値を作らない**。未確認の情報は「未確認」と明記する。
- **確認済みの事実と、自分の推測・仮説を区別する**。推測を事実として MEMORY.md や docs/ に書かない。
- **テストセットは最終評価にしか使わない**。ハイパーパラメータ調整や手法選択に使わない。
- **データ分割・評価指標・比較条件を、結果を見てから変えない**。変えるなら先に理由を述べ、承認を得る。
- 結果が悪かったときに、指標や設定を黙って変えて改善したように見せない。失敗した実験も記録する。
- **私がコードを変更していたら、意図を推測せずに尋ね、回答をログに記録する**。勝手に元に戻さない。
- **公開されていないデータや、利用条件のわからないデータを扱うことになったら、作業を止めて確認する**。
- 秘密情報・個人情報・データの中身を logs/ や docs/ に書かない（リポジトリは研究室から見える）。
- 新しい外部ライブラリの追加、データ・過去の結果の削除や上書き、長時間（目安1時間超）の実行は、先に確認する。
- **質問や見積もりに答えるために、実験・計測・重い処理を勝手に実行しない**。見積もりを聞かれたら推測で答え（推測と明記する）、実測が必要なら先に確認する。
- 既存のコード（特に指導教員・共同研究者のもの）を直すときは、依頼された範囲で、目的に必要な**最小限の差分**にする（ついでの書き換え・整形・名前の変更・コメントの追加をしない）。他人のファイルを変える前には確認する。
- `git push --force` や履歴の書き換えはしない。
- **コミットもプッシュも、依頼されるまでしない**（変更履歴が見にくくなるため。記録の `notes:` コミットも同じ）。コミットしてよい区切りでは、コミットの内容を提案するだけにする。

## 5. いつ何を使うか

| 場面 | 使うもの |
|---|---|
| 研究上のイベント（意思決定・実験・考察・研究に影響するコード変更・意図確認）が起きた | `research-log` Skill |
| ミーティング・ゼミで決まったことを伝えられた | `meeting-note` Skill |
| 関連研究・SOTA・ライブラリの仕様など、最新情報の確認が必要 | `lit-check` Skill |
| 関連研究を体系的に調べる・論文を読んでノートにする・研究ギャップを探す | `literature` Skill |
| 実験の計画・実行・結果の比較や報告 | `experiment` Skill。実行は `docs/how_to_run.md` の手順で |
| 研究課題・仮説・手法・実験設計を扱う | `docs/research_context.md` を読む |
| 前処理・データ分割・評価を触る | `docs/datasets.md` を読む |
| 関連研究を引用・比較する | `docs/papers/README.md`（目次）で探し、該当するノートと `docs/related_work.md` の比較表を読む |
| ブランチを作る・名前を決める | `CONTRIBUTING.md` を読み、`docs/experiments.md` に1行足す |
| 実験の結果が出た | **`docs/results.md` に1行足す**（`docs/how_to_run.md` §4）。`docs/experiments.md` の該当行（状態・結論）も更新する |
| 結果・数値を探す・引用する（MEMORY.md・報告・発表・卒論） | まず `docs/results.md` を見て、原本（最終の表）のファイルで値を確かめる。どの行から取ったか分かるようにする |
| ブランチをマージした・不採用にした | `docs/experiments.md` の該当行（状態）を更新する（ブランチは削除しない） |
| 区切りがついた・人に見せた/報告した・大きく方針を変える直前・ブランチを不採用にした | **自分の判断でタグを付けて報告する**（決まった場面ごとに機械的に付けない）。付け方は `CONTRIBUTING.md` の「タグ」。プッシュはユーザーが行う |

- MEMORY.md の「確定した設計判断」「検討したが却下した選択肢」には、今の作業に効いているものだけを置く。覆った判断や終わった段階の判断は、実験の段階の区切りか MEMORY.md が 5000 文字を超えたとき（`.research-memory.json` の `memory_max_chars` を超えると読み込みが切れるため）に、日付とログへのリンク付きで `docs/decisions.md` に移す（移す前にユーザーの承認を得る）。
- セッション開始時に MEMORY.md と当日のログの目次が自動で渡される。内容が実装と食い違っていたら、作業前に確認する。
- 運用ルールやユーザーの好みは、Claude Code の auto memory ではなく `AGENTS.md`・`CONTRIBUTING.md`・`docs/` に書く（auto memory は Git に残らず、ほかのサーバーや人に伝わらない）。auto memory にも書いた場合は、同じ内容をリポジトリに書いたか確かめる。
- コードを変更したら、そのたびに「何を・なぜ・挙動への影響・どう確認したか」を説明する。リファクタリングと挙動の変わる変更は分けて報告する。
- 要件や依頼の意図が曖昧なら、実装の前に質問する（多くても3つ）。選択肢を示すときは、私が前に選ばなかった案を出し直さない。
- ファイルを変える前に、何をどこにどう変えるかの結論を先に示す。「まだ変えないで」と言われたら案だけを示す。
- コマンドや環境に自分で何かを足したとき（計測用の `time`・ログ用の `tee`・追加のオプションなど）は、足したことと、結果や速度に影響しうるかを伝える。
- 現在のフェーズが「執筆中」になったら、`docs/claims.md`（論文・発表で使った数値 → 根拠の実験ID の対応表）の導入を提案する。`docs/results.md` を元に作る。

- [ ] 数値・出典を確認し、未確認のものは明記した
- [ ] 変更点・確認方法・未確認のことを報告した
- [ ] ブランチの作業を終えるとき・大きな区切りでは、次のセッションが MEMORY.md とログだけで続きを始められるかを点検した（まだ起きていないことを済んだ前提で書いていないか、も含む）
