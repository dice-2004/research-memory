# ブランチとタグの決まり

個人研究（卒論〜修士）向けのブランチ命名・運用ルール。ブランチを作るとき・タグを付けるときに読む。

> 研究室に既存の慣習がある場合は、そちらを優先して書き換える。

## 書式

```
<種別>/<NNN>_<内容を表す短い名前>
```

- 英語・小文字。番号と名前の間はアンダーバー（`_`）、名前の中の単語はハイフン（`-`）で区切る（kebab-case）
- 短い名前は3〜5単語まで
- 日本語・大文字・スペースは使わない
- `NNN` はリポジトリ内の3桁ゼロ埋め連番（`000` から開始）

## 種別

| 種別 | 用途 | 例 |
|---|---|---|
| `exp` | 実験（手法の変更・ハイパラ検証など） | `exp/001_int8-ptq` |
| `baseline` | 比較対象の再現・実装 | `baseline/002_patchcore` |
| `fix` | バグ修正 | `fix/003_dataloader-resize` |
| `chore` | 環境整備・設定・依存更新 | `chore/000_agent-setup` |
| `docs` | ドキュメントのみの変更 | `docs/004_update-readme` |
| `refactor` | 挙動を変えない整理 | `refactor/005_split-config` |

必要になったら足す: `ablation`（アブレーション）、`repro`（先行研究の再現）、`analysis`（結果の分析・可視化）、`dataset`（データ前処理）、`release`（公開用コードの整形）。

## 連番のルール

- 番号は種別をまたいだ**通し番号**（`chore/000_...` → `exp/001_...` → `fix/002_...`）
- 新規ブランチは既存の最大番号 + 1
- 番号は再利用しない（欠番は許容）
- **番号は実験IDとしても使う**（ブランチ `exp/001_...` の実験IDは `exp-001`、結果は `<結果の置き場>/exp-001_<名前>/`）。**変更を加えて実験をやり直すときは、新しいブランチ（新しい番号）にする**。ブランチを作ったら `docs/experiments.md` に1行足す
- 複数人・Issue 管理の運用になったら、Issue 番号方式（`exp/12_int8-ptq`）へ切り替える

## 運用ルール

- `<master / main>` は常に動く・再現できる状態にし、直接コミットせず MR（PR）経由でマージする
- 1ブランチ1目的（実験なら1仮説）。複数の実験を混ぜない
- 節目（中間発表・卒論提出・論文投稿など）はブランチではなく**タグ**で固定する（下の「タグ」）
- **ブランチは一切削除しない**（マージ後も、不採用でも残す。MR のマージ時の「ブランチを削除」は外す。Claude Code が誤って作った使い捨てのブランチ（`worktree-bridge-*` など）だけは例外）。マージしたら `docs/experiments.md` の「状態」を更新する
- 不採用の実験は、結果をログと `docs/experiments.md` に残し、`archive/` タグを付ける（ブランチはそのまま残す）

## Claude Code との作業場所

Claude Code（remote-control を含む）は、ユーザーと**同じフォルダ（このリポジトリのメインのフォルダ）・同じブランチ**で作業する（worktree 方式は使わない）。

- remote-control は `--spawn same-dir` で起動する。`--spawn worktree` にすると、セッションごとに worktree と使い捨てのブランチ `worktree-bridge-cse_<ID>` が作られ、取り違えの元になる。
- **セッションの最初**に、Claude が `pwd` と `git branch --show-current` で、メインのフォルダの規則どおりのブランチにいるかを確かめる。worktree の中や `worktree-bridge-*` の上にいたら、作業の前にユーザーに伝える。
- **ブランチは Claude が用意する**。新しい作業では、最新の `<master / main>` から規則どおりの名前で作る（名前は Claude が案を出し、ユーザーが確認する）。`docs/experiments.md` に1行足す。
- **Claude の作業中は、ユーザーはファイルの編集とブランチの切り替えをしない**（見るのはよい）。同じフォルダを同時に触ると変更がぶつかるため。
- 誤って作られた worktree と使い捨てのブランチは消してよい。消す前に、未保存の変更がないこと、中のコミットが規則どおりのブランチに入っていることを確かめる。

## タグ

決まった場面ごとに機械的に付けるのではなく、**人が「あとで戻りたくなる状態か」を判断して付ける**。エージェントが判断してタグを作り、作ったら報告する。プッシュはユーザーが行う。

### 付ける場面

| 場面 | 名前の例 | 理由 |
|---|---|---|
| 区切りがついて、次の作業の土台になる状態 | `repro-baseline-done` | 次で何か壊れても、正しく動いていた状態に戻れる |
| 人に見せた・報告した状態（ゼミ・教員への報告・中間発表・卒論提出・論文投稿） | `seminar-2026-11-05`、`v0-midterm`、`v1-thesis-submit` | 「あのとき見せた結果はどのコードか」に答えられる |
| 大きく方針を変える直前（評価方法の変更・手法の切り替え・大きな作り直し） | `before-<変更の名前>` | うまくいかなかったときに戻れる |
| 数値を発表・卒論に使った状態 | （上の報告・提出のタグと兼ねてよい） | 載せた数値の出どころを確かめられる |
| 実験を不採用にしたとき | `archive/<ブランチ名>` | 不採用の印になり、ブランチが増えても試したことを一覧で探せる |

付けないもの: 毎回のマージ、小さなドキュメントの修正、途中経過（数が増えると大事なタグが分からなくなる）。

`archive/` で始まるタグは、MEMORY.md の「検討したが却下した選択肢」に載っていないとセッション開始時に知らされる。不採用の理由をそこに書く。

### 付け方

- 名前は英語・小文字・ハイフン区切りで、状態が分かる短いもの（番号だけ・日付だけにしない。報告の日付は名前に入れてよい）。
- メインブランチの状態に付けるときは、MR（PR）がマージされた後に `git fetch` して `origin/<master / main>` のコミットに付ける。`archive/` は不採用にしたブランチの最後のコミットに付ける。
- 注釈付きタグにする: `git tag -a <名前> <コミット> -m "<説明>"`。説明には、どんな状態か・何を確かめたか・対応する `docs/results.md` の行・なぜ付けたかを日本語で書く。
- 付けたら `docs/experiments.md`（不採用なら「状態」の列）とログに書き、ユーザーに `git push origin <名前>` を伝える。
- プッシュしたタグは付け直さない（ほかの人の手元とずれる）。プッシュ前なら `git tag -d <名前>` で消して付け直してよい。

## 避けること

- `test`, `tmp`, `new2`, `final`, `final-final` など意図が不明な名前
- 日付だけ・番号だけの名前（何の実験か分からなくなる）
- 区切りの混在（`000-agent-setup` や `000_agent_setup` ではなく `000_agent-setup`）
- 提出時点の状態をブランチだけで管理すること（後の変更で再現できなくなる）
